\begin{abstract}
Small-scale farm ponds are a vital rainwater-harvesting intervention for mitigating seasonal drought and enhancing agricultural resilience across rural India. However, traditional manual site-selection approaches rely on labor-intensive, ad-hoc topographical field surveys that struggle to analyze spatial hydrology across extensive areas. This project presents a high-throughput, web-based geospatial decision-support system designed to identify optimal village pond locations, delineate catchment boundaries, and calculate expected annual rainwater runoff. Built on an interactive Leaflet GIS interface, the user selects any arbitrary agricultural parcel or village boundary via polygon and rectangle drawing tools. The backend processes contour maps to construct high-resolution Digital Elevation Models (DEMs), executes Priority-Flood sink filling, delineates D8 hydrological flow routing, and computes a multi-criteria Pond Suitability Index (PSI) combining depression depth, upstream flow accumulation, topographic wetness index (TWI), and relative slope elevation. 

To achieve sub-second interactive latency while serving hundreds of concurrent village administrators, the system decouples heavy one-time terrain modeling from lightweight, millisecond-scale polygon queries. The architecture is deployed as a horizontally scaled cluster across four multi-core lab systems (120 CPU cores each) orchestrated by a custom Layer-7 Load Balancer implemented in Go, featuring least-inflight connection routing, active health probes, and admission control. Under stress testing with 200 concurrent users, the distributed cluster sustained 138.7 requests per second with a 95th-percentile latency under 120\,ms and 0\% error rates, compared to severe saturation on a single-node deployment. The production web application is live and publicly accessible at \url{http://10.1.75.51:5237/}, with an accompanying video demonstration at \url{https://youtu.be/EMeGVMf4Mug}.
\end{abstract}

\section{Introduction}
\label{sec:intro}
Rural water security remains one of the most pressing socio-economic challenges in arid and semi-arid regions of India. Monsoon rainfall is concentrated within a few intense spells, leading to rapid surface runoff and prolonged dry-season soil moisture deficits. Village farm ponds harvest local surface runoff during high-precipitation events, recharging shallow aquifers and providing supplementary irrigation during critical crop growth stages. Despite their proven efficacy, planning where to dig a pond is fraught with technical complexity. A poorly situated pond either fails to capture sufficient runoff or gets overwhelmed by excessive sediment and river flooding. 

The primary goal of this assignment is to develop an end-to-end, high-performance, AI- and geospatial-assisted web application that allows users to interactively draw land boundaries on a map and instantly receive mathematically validated pond locations, upstream catchment boundaries, and annual water harvest estimates. The system must run across four designated physical cluster nodes and handle high concurrency gracefully. 

This report is organized as follows: Section~\ref{sec:requirements} defines the functional and non-functional requirements. Section~\ref{sec:architecture} details the system architecture and technology stack. Section~\ref{sec:methodology} elaborates on the terrain processing and hydrological algorithms. Section~\ref{sec:implementation} describes backend REST APIs, frontend interfaces, and memory caching. Section~\ref{sec:csd-themes} maps foundational Computer System Design (CSD) themes to our engineering decisions. Section~\ref{sec:results} presents quantitative empirical results and cluster load tests. Section~\ref{sec:discussion} reflects on system limitations, and Section~\ref{sec:ai-usage} declares AI tool usage.

\subsection{Motivation}
Manual site selection conducted by village administrators or local panchayat engineers typically relies on physical walkthroughs or static topographic sheets. These conventional methods suffer from three critical bottlenecks:
\begin{enumerate}
    \item \textbf{Topographical Complexity:} Identifying natural drainage depressions and ridge lines over undulating terrain requires calculating slope gradients and hydraulic flow vectors that cannot be intuitively gauged by eye.
    \item \textbf{Catchment Computation Bottlenecks:} Calculating the exact contributing catchment area draining into a candidate point requires recursive flow tracing across large spatial grids, a task virtually impossible without automated GIS tools.
    \item \textbf{Inaccessibility for Non-Technical Users:} Standard desktop GIS packages (e.g., QGIS, ArcGIS) require significant domain expertise, large local dataset downloads, and manual contour processing, preventing rapid field deployment.
\end{enumerate}
An automated, browser-accessible GIS tool eliminates these barriers by abstracting advanced hydrological pipelines behind an intuitive web interface that produces actionable results in milliseconds.

\subsection{Scope of the Project}
The system covers:
\begin{itemize}
    \item Ingestion and validation of standard contour data (KML/KMZ formats) and automatic UTM coordinate projection.
    \item Digital Elevation Model (DEM) construction, sink filling, D8 flow accumulation, and river corridor buffer masking.
    \item Dynamic parcel-restricted queries via interactive Leaflet bounding rectangles or arbitrary free-form polygons.
    \item Automated recommendation of up to four optimal pond sites ranked by suitability, exact upstream catchment polygons, and scale pond footprint geometries.
    \item Rational-method annual runoff volume estimation ($Q = C \cdot P \cdot A$) and pond storage capacity sizing.
    \item Layer-7 load balancing, health monitoring, and horizontal scaling across four multi-core Linux nodes.
\end{itemize}
The system explicitly does \emph{not} cover civil geotechnical engineering (e.g., soil permeability drilling, embankment slope stability, masonry spillway design) or legal cadastre ownership verification.

\subsection{Non-Functional Requirements}
\begin{itemize}
    \item \textbf{N1 -- Interactive Latency:} Bounded-area user queries must execute in well under 100\,ms to maintain seamless user interaction during interactive map exploration.
    \item \textbf{N2 -- Horizontal Scalability:} The workload must distribute evenly across the four physical lab nodes without single-worker bottlenecks.
    \item \textbf{N3 -- Overload Protection \& Graceful Degradation:} When concurrency exceeds worker capacity, incoming traffic must be queued with bounded timeouts (15\,s) and gracefully shed via HTTP 503 (\texttt{Retry-After}) rather than cascading into worker process crashes.
    \item \textbf{N4 -- Fault Tolerance:} Automatic health probing must detect crashed or lagging backend nodes within 2 seconds, dynamically routing active traffic to surviving nodes.
    \item \textbf{N5 -- Robust Validation:} Invalid polygon selections (e.g., area $<0.5$\,ha, $>50$\,km$^2$, or falling outside available contour coverage) must be rejected immediately with clean HTTP 422 error messages.
\end{itemize}

\section{Methodology}
\label{sec:methodology}
To achieve interactive latency, the hydrological pipeline is strictly partitioned into two operational stages:
\begin{itemize}
    \item \textbf{Stage A (Terrain \& Hydrology Synthesis):} Executed once when a dataset is loaded. Builds the DEM, runs sink filling, derives flow directions, and computes the Pond Suitability Index. The resulting spatial matrices are cached in process memory.
    \item \textbf{Stage B (Dynamic Parcel Query):} Executed on demand per user request. Masks the precomputed terrain models against the drawn polygon, extracts local suitability peaks, and traces upstream catchments in milliseconds.
\end{itemize}

\subsection{Terrain and Elevation Analysis}
Contour data is parsed from KML/KMZ documents containing 2,711 contour lines and 160,473 vertices. Raw geographic coordinates are projected into Universal Transverse Mercator (UTM Zone 44N, EPSG:32644) to establish Cartesian metric units:
\begin{enumerate}
    \item \textbf{Spike Filtering:} Anomalous elevation vertices outside the 1st--99th percentile window are rejected.
    \item \textbf{Grid Interpolation:} Linear barycentric interpolation discretizes the irregular contours onto a regular grid of $200 \times 161$ cells with a spatial resolution of $16.2\text{ m} \times 16.2\text{ m}$.
    \item \textbf{Surface Smoothing:} A Gaussian filter with standard deviation $\sigma = 1.0$ attenuates interpolation artifacts.
    \item \textbf{Sink Filling:} Depressions are identified using the Priority-Flood algorithm (Barnes, 2014). The water depression depth $d$ is derived as:
    \begin{equation}
        d = z_{\text{filled}} - z_{\text{raw}}
    \end{equation}
    Cells with $d > 0.05$\,m mark natural runoff collection bowls.
\end{enumerate}

\subsection{Catchment Area Delineation}
Surface runoff follows the steepest gradient across the 8-connected grid (D8 routing). Let $\Delta z_{ij}$ be the elevation drop to neighbor $(i, j)$ at distance $L_{ij} \in \{1, \sqrt{2}\}$. The flow direction points to:
\begin{equation}
    \text{dir} = \arg\max_{(i,j)} \frac{z - z_{ij}}{L_{ij}}
\end{equation}
Flow accumulation $A$ (number of upstream contributing cells) is computed via reverse topological sorting from highest to lowest elevation. River corridors are identified where $A \ge P_{95}(A)$ or where cells lie in the lowest 18\% elevation with slope $<3^\circ$. Candidate pond sites are enforced to remain $\ge \max(120\text{ m}, 0.25 d_{\max})$ away from river paths to prevent flood destruction.

The composite Pond Suitability Index (PSI) combines four normalized factors:
\begin{equation}
    \text{PSI} = 0.35\,\hat{d} + 0.30\,\widehat{\ln(1+A)} + 0.20\,\widehat{\text{TWI}} + 0.15\,(1-\hat{z})
\end{equation}
where $\hat{\cdot}$ denotes min--max normalization, $\hat{z}$ is normalized elevation, and $\text{TWI} = \ln(a / \tan\beta)$ represents the Topographic Wetness Index for specific catchment area $a$ and slope $\beta$.

When a user draws a polygon in Stage B, candidate sites are selected from the local maxima of the PSI within the polygon, constrained by:
(1) minimum upstream catchment $A \ge 1$\,ha, (2) spatial separation $\ge 350$\,m, and (3) a cap of at most 4 sites. Upstream catchment boundaries are delineated by recursively following reverse-D8 paths starting from the candidate pour point.

\subsection{Rainfall Data Integration}
Precipitation parameters are calibrated against Indian Meteorological Department (IMD) historical normals and Open-Meteo climate reanalysis archives for the central Chhattisgarh agricultural zone. Annual rainfall depth ($P$, default $850$\,mm) and surface runoff coefficient ($C$, default $0.35$ for mixed agricultural loam) are integrated into the catchment runoff model using the standard Rational Method:
\begin{equation}
    Q = C \cdot \left(\frac{P}{1000}\right) \cdot \left(A_{\text{catchment}} \times 10^4\right) \quad [\text{m}^3/\text{year}]
\end{equation}
Recommended pond capacity is determined as $V_{\text{pond}} = \min(0.18\,Q,\,25\,000)\,\text{m}^3$, assuming a typical depth $H = 3.5$\,m with 1:1.5 side slopes.

\subsection{Database and Storage}
Because all spatial analysis depends only on the dataset and the query polygon, worker nodes operate strictly statelessly. Stage A terrain matrices are kept resident in memory across Gunicorn worker forks via Python's copy-on-write memory model (\texttt{--preload}). Query responses are cached using an in-memory LRU cache keyed by SHA-256 hashes of the normalized polygon coordinates, achieving $0.2$\,ms response times for repeated queries.

\subsection{Deep-Dive on Key Engineering Decisions}
\textbf{Decoupled Stage A/B Architecture:} The most critical architectural decision was separating dataset-level terrain modeling from user-level area queries. A monolithic pipeline that processed contours on every request would take $0.9$\,s per click, making interactive map drawing unusable. Precomputing the DEM and PSI in Stage A reduced runtime query latency to under $35$\,ms.

\textbf{Custom Go Load Balancer vs. Off-the-Shelf Proxies:} Rather than deploying a generic Nginx instance, we engineered a dedicated Go load balancer (\texttt{pond\_lb.go}). This enabled custom application-aware admission control: limiting in-flight concurrency per node strictly to its worker capacity (119 requests), buffering request bodies in memory to retry on alternative backends upon HTTP 5xx errors, and providing explicit HTTP 503 shedding with \texttt{Retry-After} headers under flash crowds.

\section{Discussion and Limitations}
\label{sec:discussion}
While the system achieves outstanding computational performance and intuitive visualization, several operational assumptions and limitations remain:
\begin{enumerate}
    \item \textbf{Hydrological Simplifications:} The Rational Method assumes a uniform annual runoff coefficient ($C$) and lumped precipitation. It does not account for temporal storm intensity variations, transient soil infiltration curves (e.g., SCS Curve Number), or evaporation losses.
    \item \textbf{DEM Spatial Resolution:} The 16.2\,m interpolated grid resolution is sufficient for macro-catchment routing, but parcels under $0.5$\,ha cannot be reliably resolved.
    \item \textbf{Independent Process Caches:} When a user uploads a new custom KML file, each worker node independently recomputes Stage A on its first encounter with that file. A distributed cache (e.g., Redis) or shared filesystem volume would optimize custom uploads across nodes.
    \item \textbf{Single Point of Failure at Ingress:} While worker nodes are fully redundant, the Go Load Balancer runs on Sys1. In an enterprise environment, a secondary passive LB configured with VRRP/Keepalived would ensure high availability.
\end{enumerate}
